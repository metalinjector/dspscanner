# Локальное сравнение OCR: Tesseract, постоянный API, RapidOCR и OpenVINO

Дата: **14 октября 2026 года**. Эксперимент для DSP Scanner; производственный backend не заменялся.

<!-- RESULTS:START -->
**Все измерения завершены: 27/27 trials, 216 измеренных + 216 прогревочных страниц.** Ошибок worker/таймаутов — 0; библиотечная диагностика TIFF отдельно описана ниже.

## Основной результат

**На этом корпусе не найден альтернативный движок быстрее Tesseract Fast.** Наиболее быстрый вариант с полной контрольной полнотой — переиспользование Tesseract API: **8,545 с вместо 9,620 с за 8 страниц**, то есть снижение времени на **11,2%** относительно CLI `rus+eng`. Полный текст побайтно совпадает между CLI и API для каждой страницы и обоих языковых режимов.

Быстрейший RapidOCR — гибрид v6 Tiny detector + v5 Eslav через OpenVINO: **13,603 с**. Это на **41,4% дольше**, чем Tesseract CLI `rus+eng`, и на **59,2% дольше**, чем постоянный API.

**Важно:** русский-only вариант не является равноценной заменой `rus+eng` на смешанном корпусе. Он потерял 33 английских контрольных вхождения из 344 в каждом проходе. У остальных вариантов — 344/344; лишних контрольных вхождений, ложных находок по контрольному словарю и пустых страниц нет. Это не оценка полноты на произвольных документах.

### Практические выводы

- **Оставить Tesseract Fast основным backend.** Результат не обосновывает замену на RapidOCR ради скорости в этом окружении.
- **Постоянный API заслуживает отдельного прототипа интеграции.** Выигрыш `rus+eng` — 11,2%, `rus` — 5,9%. На короткой записке медиана снизилась с **0,424 до 0,227 с** (−46,4%); на плотных страницах эффект скромнее. Это не обещание ускорить весь scanner на тот же процент.
- **OpenVINO стоит использовать, если выбран RapidOCR.** Для одинакового v5 Eslav-конвейера время уменьшилось с 35,308 до 14,826 с — примерно в **2,38 раза**. Но даже после этого он не стал быстрее Tesseract. Измеренная память OpenVINO-вариантов около 956–999 MiB против 91–99 MiB у Tesseract `rus+eng` в этой оснастке; размер файла модели не отражает runtime-память.
- **RapidOCR не следует отвергать по качеству.** Он лучше сохраняет строки/табличный порядок в части примеров, но хуже читает порядок двух колонок. CER ниже в среднем, однако значительная часть различия связана с порядком чтения, а не подменой букв. Все полноценные RU/EN-варианты нашли одинаковые контрольные слова.
- Перед изменением production нужны реальные обезличенные сканы, длинные поисковые фразы/идентификаторы, несколько типов CPU и замер всего scanner. Заявленный в обзоре предварительный порог −20% на общей нагрузке для автоматического перехода **не достигнут**.

## Что именно проверено

Девять конфигураций:

1. Tesseract Fast CLI, `rus`.
2. Та же библиотека Tesseract через постоянный C API, `rus`.
3. Tesseract Fast CLI, `rus+eng`.
4. Постоянный C API, `rus+eng`.
5. RapidOCR: PP-OCRv5 mobile detector + Cyrillic mobile recognizer, ONNX Runtime CPU.
6. RapidOCR: PP-OCRv5 mobile detector + Eslav mobile recognizer, ONNX Runtime CPU.
7. RapidOCR: PP-OCRv6 Tiny detector + PP-OCRv5 Eslav recognizer, ONNX Runtime CPU.
8. Конфигурация 6 через OpenVINO CPU.
9. Конфигурация 7 через OpenVINO CPU.

**Конфигурации 7 и 9 — гибрид, а не русская PP-OCRv6 Tiny recognition-модель.** Здесь v6 отвечает только за поиск областей текста; распознаёт символы русская модель v5.

Для API использована небольшая `ctypes`-обёртка над `TessBaseAPI`. Это проверка гипотезы переиспользования движка, **не замер Python-пакета `tesserocr`**. Shared library собрана из тех же static archives, что CLI: версия, оптимизации и модели одинаковы. После каждой страницы очищаются результаты и adaptive classifier; модель не загружается заново. Объект не разделяется между потоками.

### Установка и происхождение весов

После пересоздания окружения прежний установленный runtime отсутствовал. В этой итерации выполнена **полная чистая сборка через `tools/install_tesseract.py --build`**, а не только проверка уже установленного бинаря. Сборка завершилась успешно; восстановлены все шесть закреплённых русских/английских моделей Fast/Standard/Best. В сравнении использован только Fast.

Для RapidOCR модельные хостинги ModelScope/Hugging Face недоступны из sandbox. Найдены GitHub-зеркала файлов ONNX. Загружены только модели, **без исполнения кода зеркал**; SHA-256 каждого файла совпал с официальным реестром RapidOCR v3.10.0. URL закреплены на конкретных commit, а не `main`: [manifest](../tools/ocr/benchmark_models.json). Словари символов встроены в ONNX. Загрузка моделей во время benchmark запрещена: попытка автоматического скачивания вызывает ошибку.

Для воспроизводимости сохранены версии зависимостей: [benchmark_requirements.txt](../tools/ocr/benchmark_requirements.txt). Эти пакеты не добавлены в production `requirements.txt`. OpenVINO telemetry отключена командой `opt_in_out --opt_out`. Документы не передавались облачным OCR.

## Методика

### Окружение и ограничения CPU

Linux x86-64, Python 3.11.2, Intel Xeon @ 2.60 GHz, доступно 2 логических CPU и около 4 GB RAM. **Каждый измеряемый worker закреплён за одним логическим CPU**; одновременно работает только один backend. Tesseract OpenMP, ONNX Runtime и OpenVINO ограничены одним вычислительным потоком. OpenCV также ограничен одним потоком.

OpenVINO фактически использовал CPU, один stream и `float32` inference precision hint; эти свойства сохранены для каждой страницы. ONNX Runtime сообщил `CPUExecutionProvider`. Измерение не использует GPU.

Это сравнение **однопоточной задержки и последовательной пропускной способности**, а не проверка двухпроцессного production-сканера. Переносить результат на любой CPU, Windows или GPU нельзя.

### Корпус

Восемь **разных синтетических страниц A4** с известной транскрипцией:

- обычный печатный русский, sans-serif;
- плотный русский текст, serif;
- русский и английский, включая `Contract`, `invoice`, `ZX-2048`;
- таблица с горизонтальными линиями;
- две колонки;
- мелкий шрифт;
- искусственно ухудшенная страница: наклон 1,3°, blur, пониженный контраст, шум, JPEG-сжатие;
- короткая записка.

Использованы DejaVu Sans/Serif с сохранёнными хешами шрифтов. Сначала страницы растрируются в 250 DPI и встраиваются в image-only PDF, затем одним путём рендерятся в **150 DPI, grayscale PGM**. Текстового слоя в PDF нет. SHA-256 изображений сохранены в JSON. Нет реальных пользовательских сканов, рукописи, поворотов на 90/180°, печатей и большого разнообразия шрифтов.

Всем движкам передаются одинаковые PGM-байты. Каждый выполняет собственный необходимый decode/preprocessing. Tesseract: OEM 1, PSM 3, Fast, явные 150 DPI. RapidOCR: mobile recognition, detector `limit_type=min`, `limit_side_len=736`, максимальная сторона изображения 2000; orientation classifier отключён для этого upright-корпуса. Нейросетевой recognizer самостоятельно нормализует вырезанные строки. Конфигурации сохранены в JSON.

### Повторы, прогрев и время

- Три независимых worker-процесса на каждый backend.
- В каждом worker сначала прогревается **весь** корпус, а не только несколько чистых страниц.
- Затем измеряется весь корпус с циклически сдвинутым порядком страниц.
- Порядок backend также циклически сдвигается между повторами.
- Всего 27 worker trials, 216 измеренных распознаваний страниц и 216 прогревочных.
- Основное число — медиана суммарного времени восьми измеренных страниц.
- `p50/p95` характеризуют время страницы в смешанном корпусе, не доверительный интервал.
- Cold-показатель включает импорт/подготовку backend и первое распознавание, но **не** Python process spawn и предварительное чтение корпуса. Кэш ОС не сбрасывался: это не cold boot машины.

OCR-таймер включает decode, подготовку изображения, запуск CLI (для соответствующей конфигурации), inference и получение текста. **Рендер PDF, обход файлов, поиск терминов, GUI и экспорт не входят в OCR-таймер.** Рендер измерен отдельно один раз при генерации корпуса и не объявляется самостоятельным надёжным benchmark.

### Качество

1. Полнота **344 контрольных вхождений на корпус** — основной показатель для задачи поиска. Считаются literal-подстроки после NFC, casefold и нормализации пробелов; нет исправления `ё/е`, латинских букв вместо кириллических или `O/0`.
2. Отдельно считаются пары «страница — термин»: потерять одно повторение слова и совсем не найти документ — разные ошибки.
3. Проверяются лишние вхождения и ложные находки по контрольному словарю, включая отрицательные запросы.
4. CER/WER считаются по известному тексту, с тем же ограниченным нормализатором.
5. Сравниваются хеши полного OCR-текста между повторами, прогревом и измерением, а также CLI/API.

**Важная оговорка CER/WER:** порядок чтения влияет на Levenshtein. Tesseract может отделять колонку нумерации от основного текста, а RapidOCR — читать две колонки построчно слева направо. Поэтому большой CER не равен такому же проценту неверно распознанных букв. Для поиска отдельных слов контрольная полнота информативнее. Этот корпус не доказывает превосходство качества на реальных архивах.

Память — максимальная выборка суммы RSS worker и его дочерних процессов каждые 10 мс. Это не размер весов, не пик памяти всего DSP Scanner и не точный PSS: общие страницы процессов могут учитываться дважды, короткие пики могут не попасть в выборку.

### Диагностика Tesseract

Закреплённая облегчённая сборка Leptonica не содержит TIFF decoder. При инициализации наблюдаются сообщения `pixReadMemTiff: function not present`, `pixaGenerateFontFromString` / `bmfCreate` о загрузке встроенного bitmap-шрифта. Они сохранены в `stderr` отчёта. CLI возвращает код 0 и непустой текст; API также выдаёт текст. **Нельзя называть этот запуск полностью свободным от предупреждений.** Сравнение относится именно к этой сборке; отдельная полнофункциональная сборка с TIFF потребовала бы повторного замера.

## Как воспроизвести

Linux, C/C++ toolchain и make. Все большие runtime/model/corpus-файлы остаются под игнорируемыми каталогами, в Git сохраняются только скрипты, manifest и отчёт.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r tools/ocr/benchmark_requirements.txt
.venv/bin/opt_in_out --opt_out

# Чистая сборка закреплённого Tesseract + все модели:
.venv/bin/python tools/install_tesseract.py --build --jobs 2

# Экспериментальная C API-библиотека из ТОЙ ЖЕ сборки:
g++ -shared -Wl,--whole-archive Tesseract-OCR/lib/libtesseract.a \
  -Wl,--no-whole-archive Tesseract-OCR/lib/libleptonica.a \
  Tesseract-OCR/lib/libpng16.a Tesseract-OCR/lib/libjpeg.a \
  Tesseract-OCR/lib/libz.a -fopenmp -Wl,-z,defs \
  -o Tesseract-OCR/lib/libtesseract-benchmark.so

# Загрузка разрешена только здесь, веса проверяются по upstream SHA-256:
.venv/bin/python tools/benchmark_ocr_engines.py --download-models --repeats 3

# Для повторного офлайн-запуска убрать --download-models.
# При других шрифтах/путях использовать --font-dir /path/to/dejavu.
```

Ожидаемая длительность зависит от CPU: benchmark намеренно выполняет 432 распознавания последовательно, а не имитирует статистику пересчётом одной страницы в pages/min.

## Что не проверялось

- Яндекс: облачный OCR не вызывался; пользовательские данные не отправлялись.
- Windows.Media.Ocr: здесь Linux, не Windows.
- ABBYY/Smart Text Engine: нет production/trial-лицензий полного движка; mock SDK не считается тестом качества.
- Community PP-OCRv6 Tiny RU recognizer: опубликован через недоступный здесь Hugging Face; в проверенном GitHub-репозитории автора нет весов или release assets. Не путать с протестированным Tiny **detector**.
- EasyOCR, Surya и OCR-VLM: в этот CPU-эксперимент не включались. Это ограничение объёма проверки, а не доказательство невозможности их установить или их низкой скорости.
- Реальный пользовательский корпус, Windows packaging, многопроцессный scanner end-to-end и долговременное поведение памяти.
