# Русский OCR и аудит DOC / DOCX / TXT

**Завершено 14 октября 2026 года.** Изменены исходники программы, добавлены регрессионные тесты и воспроизводимый benchmark. Windows EXE в Linux-окружении не собирался.

## 1. Принудительно только русский

Настройка `russian_only` **уже существовала**, по умолчанию `True`, но при отсутствии русской модели могла переключаться на английскую. Теперь это строгий режим:

- GUI: **Настройки → Параметры → Внешние программы → «OCR: принудительно только русский (rus)»**.
- CLI: `--russian-only`; для русского и английского — `--no-russian-only`.
- Окружение: `DSP_SCANNER_RUSSIAN_ONLY=true` / `false`.
- При отсутствии `rus.traineddata` выводится явное предупреждение; переход на `eng` запрещён. Растрирование/повтор OCR на другом DPI не запускается ради отсутствующей модели.
- Сохранение и загрузка выбора проверены для обоих значений. Существующий пользовательский выбор **не сбрасывается**.

Это настройка **OCR сканированных PDF**, не фильтр готового текста. DOC, DOCX, TXT и PDF с текстовым слоем продолжают находить английские слова, если они указаны в запросе. Отбрасывать латиницу ради неподтверждённого «ускорения» не стали.

Ускорение подтверждено предыдущим локальным [OCR benchmark](OCR_ENGINE_BENCHMARK_2026-10-14.md): Fast CLI `rus` — 8,248 с, `rus+eng` — 9,620 с за 8 страниц (**−14,3%**); постоянный API — 7,761 против 8,545 с (**−9,2%**). Это один синтетический корпус, не гарантия для любого PDF; английские контрольные слова в `rus` были потеряны. Реальный OCR в текущей итерации повторно не запускался.

## 2. DOC: основной риск был в извлечении, а не в поиске

### Что было

«Авто» искал похожие на слова последовательности в бинарном `WordDocument`. Это эвристика, не восстановление логического текста Word. Она могла включать служебные данные, терять пунктуацию и слова короче трёх символов. На контрольном документе **все 500 вхождений «РФ» терялись**. Наличие непустой строки не доказывало полноту чтения.

### Что исправлено

Добавлен `app/readers/ole_doc.py`: разбор **FIB → CLX → PlcPcd / текстовых фрагментов Word 97–2007**. Поддерживаемые FIB версии перечислены в коде. Логический порядок берётся из CP/PCD, а не из физического размещения байтов:

- Unicode UTF-16LE и compressed Windows-1252 pieces;
- короткие слова, номера, пунктуация, границы абзацев/ячеек;
- текстовые результаты полей вместо скрытых команд `HYPERLINK` и других инструкций;
- проверка диапазонов, монотонности CP, ограничений количества фрагментов и итогового размера текста;
- парольная защита приводит к понятной ошибке, а не к поиску «слов» в шифротексте.

Каскад AUTO теперь: **структурный разбор → эвристика с предупреждением → внешние программы при неудаче**. Явный выбор LibreOffice/COM/эвристики сохранён. Варианты RTF/HTML/Word 2003 XML/DOCX под расширением `.doc` продолжают определяться по содержимому. Исправлены границы inline/block в HTML и Word XML, короткие тексты и объявленная RTF-кодировка.

**Ограничения:** это извлечение текстовых потоков, не движок отрисовки Word. Нет OCR встроенных картинок, обхода всех вложенных объектов и гарантии совпадения с отображением всех правок/скрытых фрагментов. Word 6/95 и неподдерживаемые/повреждённые структуры могут перейти к приблизительной эвристике; она теперь явно предупреждает о возможных пропусках. Для ответственного полного разбора таких DOC следует выбрать внешний конвертер. LibreOffice и MS Word COM здесь не запускались.

### Проверка на внешних файлах

Использованы шесть DOC из публичного тестового набора Apache POI: `simple.doc`, `simple-table.doc`, `SimpleHeadThreeColFoot.doc`, `o_kurs.doc` (русский), `HeaderFooterUnicode.doc`, `PasswordProtected.doc`.

В пяти нешифрованных файлах получен текст через piece table; парольный файл корректно отклонён. Это **smoke-проверка совместимости**, не независимая оценка полного текста каждого документа. Файлы не включены в Git; закреплённые Git blob URL, входные/выходные хеши и исходы сохранены в [JSON](benchmarks/doc-external-fixtures-2026-10-14.json). Макросы не выполнялись.

## 3. DOCX: устранены пропуски и ложная кратность

Основным остаётся прямой безопасный XML-разбор, а не дорогой обход таблиц `python-docx`.

Исправлено:

- раньше читался только **первый** MHTML/altChunk; теперь обрабатываются все найденные MHT/MHTML-разделы;
- одинаковые реальные разделы не выкидываются: два вхождения должны оставаться двумя;
- MIME `multipart/alternative` не превращает HTML и plain-версию одного раздела в две находки;
- HTML entities (`&amp;` и др.) декодируются, inline-разметка не разбивает слово «Дого» + «вор»;
- вложенные текстовые блоки, абзацы, ячейки и неразрывные дефисы имеют корректные границы;
- поддержаны transitional и strict WordprocessingML namespaces;
- повреждённая вспомогательная XML/MHTML-часть не скрывает остальные части; частичное извлечение сопровождается предупреждением;
- документ только из MHTML не запускает ненужный `python-docx` fallback и повторное открытие архива.

Сохранены лимиты размера/степени сжатия ZIP и безопасный XML parser. **Ограничения:** поддержка altChunk здесь относится к MHT/MHTML, не ко всем возможным OOXML relationship types. Изображения, некоторые схемы/объекты и точный визуальный порядок Word не гарантируются. Некоторый текст колонтитулов/комментариев читается намеренно, даже если не отображается в основном теле документа.

## 4. TXT: корректность кодировки и быстрый UTF-путь

- Сохранён приоритет BOM: UTF-32 проверяется до UTF-16, чтобы не перепутать общий префикс `FF FE`.
- Добавлена консервативная структурная проверка UTF-16/32 без BOM; отдельно проверены короткий «РФ» и греческий UTF-16.
- Корректный UTF-8 с tab/form-feed не отправляется без необходимости в полный определитель кодировки.
- Воспроизведена ошибка: короткий Windows-1251 «Договор» определялся как Shift-JIS; смешанный RU/EN мог определяться как CP1250. Для коротких **низкоуверенных** результатов добавлен приоритет CP1251/KOI8-R/CP866.
- Неустановленная точно legacy-кодировка отмечается предупреждением, а не выдаётся за достоверную. Проверены также UTF-8 с китайским текстом и отдельные западноевропейские примеры.

**Ограничение:** автоматическое распознавание произвольной кодировки без метаданных принципиально неоднозначно. Русский приоритет может быть неподходящим для некоторых коротких иностранных legacy-строк. Для критичных/неоднозначных файлов рекомендуется пересохранение в UTF-8 (или Unicode с BOM). Настройка русского OCR не управляет этим алгоритмом и не удаляет иностранный текст.

## 5. Общий алгоритм поиска и сканер

- Готовый текст ищется без OCR: regex для небольшого списка/сложных запросов, Aho–Corasick для большого списка литералов (порог 32).
- Исправлено расхождение `re.IGNORECASE` и Aho для латинской `I` / dotless `ı`: число находок не должно меняться из-за длины списка терминов. Проверены также кириллица, `е/ё`, целые слова, wildcard и фразы через перенос.
- Пропуск чтения при поиске только по имени, ограничения размера, отмена, таймауты и process isolation сохранены.
- DOC по-прежнему обрабатывается в отдельном spawn-процессе. В коротких файлах **запуск процесса существенно дороже самого чтения**. Изоляция не удалена ради красивых цифр; постоянный пул потребовал бы отдельного решения по таймаутам и восстановлению после зависаний.

## 6. Измерения до/после

Скрипт: [benchmark_text_readers.py](../tools/benchmark_text_readers.py). Корпус создаётся [text_corpus.py](../tools/text_corpus.py); бинарный DOC — собственная синтетическая CFB-фикстура, **не** документ, пересохранённый MS Word.

Linux, Python 3.11, 2 CPU. Семь повторов, прогрев, чередование старого и нового читателей, тёплый файловый кэш. Старые читатели загружаются из фиксированного базового commit `f5c09ad70d809e6931c13e34700deb7da0296e10`; хеши исходников сохранены. Таймер чтения не включает последующий поиск и генерацию контекста. На больших примерах ожидается 500 вхождений каждого из трёх контрольных терминов.

| Файл / 500 строк, кроме короткого TXT | До, мс | После, мс | Контрольные находки |
|---|---:|---:|---|
| `utf8.txt` | 0.188 | 0.069 | 1500/1500 → 1500/1500 |
| `cp1251.txt` | 1.500 | 1.448 | 1500/1500 → 1500/1500 |
| `short-cp1251.txt` | 0.175 | 0.248 | 0/1 → 1/1 |
| `utf16-no-bom.txt` | 6.993 | 1.979 | 1500/1500 → 1500/1500 |
| `paragraphs.docx` | 2.511 | 3.117 | 1500/1500 → 1500/1500 |
| `table.docx` | 3.309 | 4.288 | 1500/1500 → 1500/1500 |
| `unicode.doc` | 1.398 | 1.893 | 1000/1500 → 1500/1500 |

**Не всё ускорилось.** Более полный разбор DOC/DOCX немного дороже старой эвристики/упрощённого XML-прохода на этих простых примерах. Это осознанная плата за корректность; не утверждается ускорение всей программы в разы. Для короткого CP1251 исправлена потеря слова, а не улучшено время чтения.

На неизменном Unicode-тексте с 64 запросами (3 положительных, остальные отсутствуют) авто-поиск занял **7.141 мс**, принудительный regex — **42.272 мс**; находки и позиции совпали. На трёх запросах regex немного быстрее принудительного Aho. Это проверка существующего выбора алгоритма, не универсальная настройка порога для любого корпуса.

### Полный текущий сканер

По три файла каждого формата, два workers, три повтора; лимит 3 совпадения на термин/файл, русский OCR включён. Английский `contract` продолжает находиться во всех форматах. Для TXT использован UTF-8, поэтому нет предупреждений об угадывании кодировки.

| Формат | Три файла, медиана, с | Находки / ошибки |
|---|---:|---|
| `.doc` | 0.327 | 27 / 0 во всех 3 повторах |
| `.docx` | 0.018 | 27 / 0 во всех 3 повторах |
| `.txt` | 0.008 | 27 / 0 во всех 3 повторах |

Это отдельный end-to-end замер **текущего** сканера; старый сканер целиком не сравнивался. Нельзя выдавать разницу форматов за ускорение до/после.

Дополнительный CLI smoke с `--russian-only`: три файла (DOC/DOCX/CP1251 TXT), **9 находок**, экспорт CSV успешен. Выдано одно предупреждение об эвристически определённой CP1251; CLI показывает его в общей категории «ошибки/предупреждения». Это не сбой извлечения текста.

Все исходные измерения: [text-readers JSON](benchmarks/text-readers-linux-2026-10-14.json).

## 7. Проверки и воспроизведение

Финальная локальная проверка: **224 passed, 10 skipped**, Ruff / compileall / `git diff --check` — успешно. Пропуски: GUI (PySide6 отсутствует), 8 opt-in реальных OCR-тестов, 1 тест необязательного OCR-корпуса. Не следует выдавать эти пропуски за выполненное GUI/Windows/OCR-тестирование.

Новые тесты покрывают строгий язык и сохранение настроек, матрицу кодировок, импортированные DOCX-разделы, XML-границы, внутренние ограничения DOC, смешанные compressed/Unicode pieces и их логический порядок, парольную защиту, несовпадения regex/Aho и **настоящий spawn-путь сканера для DOC** вместе с DOCX/TXT.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements_cli.txt pytest ruff
.venv/bin/python -m pytest -ra
.venv/bin/python tools/benchmark_text_readers.py --compare-baseline --scanner --repeats 7
```

`--compare-baseline` исполняет только код читателей из указанного фиксированного commit этого репозитория. Сгенерированные документы остаются в игнорируемой `.venv/doc-audit/`; в Git не включены большие корпуса, runtime и пользовательские документы. Тестирование не использует облачный OCR.
