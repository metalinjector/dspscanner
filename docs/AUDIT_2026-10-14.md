# Аудит DSP Scanner: OCR, производительность и надёжность

> Обновление следующего этапа: установлен реальный Tesseract 5.5.3, проверены Fast/Standard/Best и оба языковых режима. См. [установку и реальные замеры](OCR_SETUP.md). Ниже сохранён исходный аудит до установки движка.

Дата: 2026-10-14. Исходная версия: `f5c09ad`, 4.6.0.0. Проверка изменений — Linux x86_64, Python 3.11.2, PyMuPDF 1.28.2, 2 логических CPU.

## Краткий вывод

**Переключение Fast само по себе не устраняет накладные расходы конвейера.** В исходном коде оно меняет каталог моделей, но при отсутствии каталога происходит молчаливый откат. Помимо самой нейросети время расходуется на запуск изолированного Python-процесса для каждого PDF, загрузку моделей для каждой страницы, растеризацию/PNG, ожидание пачек и повторный OCR. Для большого PDF к этому добавляется общий таймаут файла в 60 секунд.

Внесены локальные исправления конвейера, конфигурации и две независимые правки корректности. **Не заявляется ускорение полного OCR в N раз:** в среде нет Tesseract и пользовательского корпуса. Измеренное ускорение относится только к подготовке изображений.

### Как применён подход Карпати

Здесь это практический цикл, а не приписываемый автору формальный стандарт:

1. Понять данные, ограничения и весь путь исполнения, прежде чем менять алгоритм.
2. Зафиксировать baseline, собрать минимальные воспроизводимые примеры ошибок.
3. Проверять простые гипотезы и делать абляции: RGB/PNG → gray/PNG → gray/PGM.
4. Менять ограниченный участок, сохранять семантику, проверять регрессии.
5. Отделять измеренный результат от гипотез; крупные изменения принимать только после проверки скорости **и полноты поиска**.

## 1. Архитектура и сильные стороны

Путь сканирования:

```text
GUI ScanWorker / CLI
  → DocumentScanner.run
  → предварительный обход → ограниченная очередь os.scandir
  → пул файлов
  → для PDF/DOC: semaphore → spawn отдельного Python-процесса
  → извлечение текстового слоя → OCR недоступных/битых страниц
  → поиск regex / Aho–Corasick → контексты → результаты файла
  → GUI / экспорт / SMTP
```

Уже сделано правильно:

- `os.scandir`, дедупликация файлов, ограниченные очереди, отсутствие Future на каждый файл архива;
- отдельные процессы для рискованных ридеров, принудительное завершение при таймауте/отмене;
- пропуск чтения содержимого при поиске только по имени;
- прямой XML-путь DOCX, лимиты ZIP/XML и `defusedxml`;
- ограничение числа пикселей OCR и попытка не распознавать уже текстовые страницы;
- пакетная доставка результатов файла в GUI;
- атомарная запись настроек, защита CSV/XLSX от формул;
- проверка SHA-256 перед разрушительным перемещением, ограничения symlink/hardlink, оговорки о SSD в GUI;
- отдельная headless-проверка и матрица Windows/Linux в CI.

Это стоит сохранить, а не заменять массовым переписыванием проекта.

## 2. Подтверждённые проблемы и внесённые исправления

| Приоритет | Участок | Было | Теперь |
|---|---|---|---|
| P0 | `file_operations._copy_exclusive` | На любой ошибке удалялся target, даже если `open(..., 'xb')` не создал его: возможна потеря чужого файла при коллизии имени или ошибке открытия source | Cleanup только после успешного создания собственной копии; три теста на коллизию, ошибку source и частичную запись |
| P1 | `pdf_reader._ocr_pages` | Общий `fitz.Document` использовался потоками OCR | Все обращения к документу/рендер выполняет поток-владелец; worker получает только bytes и DPI |
| P1 | Планирование страниц | Барьер после каждой пачки до четырёх страниц | Ограниченное скользящее окно: следующий OCR запускается после освобождения любого слота |
| P1 | Ошибки OCR | `ocr_page` подавлял исключения и возвращал пустую строку; ошибки/таймауты повторялись на 250 DPI, предупреждение терялось | Ошибка видна с номером страницы; технический сбой не запускает второй проход; текст успешных страниц сохраняется |
| P1 | Поиск моделей | Отсутствие fast-каталога было незаметно; системному Tesseract мог подставляться несуществующий `.../bin/tessdata`; fast требовал именно rus | Поддержаны rus или eng (русский fallback приоритетнее English-only fast); несовпадение языка также видно; сохраняется системный путь/`TESSDATA_PREFIX`, если нет переносимых моделей; fallback явно указан в предупреждении |
| P1 | CLI/config | `application.ocr_model_tier` и `russian_only` не переносились в окружение CLI; `bool('False') == True` ломал отключение режима русского языка | Добавлены `--ocr-model-tier`, `--[no-]russian-only`, перенос JSON в spawn-совместимое окружение, разбор строковых bool |
| P2 | Подготовка изображения | Цветной RGB PNG на каждую попытку | Серый PGM без PNG-сжатия; фактический DPI передаётся `--dpi`, так как PGM не хранит разрешение |
| P2 | OpenMP | Импорт модуля менял окружение всего приложения | По умолчанию один поток только в окружении дочернего Tesseract; явное пользовательское значение сохранено |
| P2 | `search_engine._find_aho_positions` | На 32 терминах включался Aho с перекрытиями, в отличие от regex: `aa` в `aaaa` давал 3 результата вместо 2 | Единая неперекрывающаяся семантика для одного термина; регрессионный тест |
| P2 | GUI | Обещания «+30% скорости», «20–30%» без условий; русский язык смешивался с градацией модели | Проценты убраны; выбор языка отделён от типа моделей, объяснён fallback |

Для copy/search сначала добавлены воспроизводящие тесты: три упали на старом коде, после минимальных правок прошли.

**Сохранены:** PSM 3, первый проход 150 DPI, повтор 250 DPI для успешно обработанных страниц с текстом короче 30 символов, выбор более длинного результата, лимит пикселей, порядок страниц, возможность отключить OCR и ограничить первые страницы. Технические ошибки намеренно больше не приравниваются к короткому тексту.

**Важное ограничение:** имя `tessdata-fast` не доказывает, что внутри действительно int8-модели. Нужен доверенный источник моделей и в дальнейшем manifest с хешами. При fallback предупреждение может повлиять на `--fail-on-scan-errors` — это намеренная видимость несоответствия конфигурации, не отказ читать документ.

## 3. Измерения и проверки

### Абляция подготовки изображений

Команда:

```bash
python tools/benchmark_ocr.py --repeats 7 --pages 4
```

Синтетический image-only A4 PDF: 4 одинаковые страницы с 45 строками английского текста, исходный растр 250 DPI, подготовка для OCR 150 DPI. Один прогрев на вариант, затем 7 замеров с чередованием порядка вариантов; таблица содержит медианы суммарного времени четырёх страниц.

| Вариант | Время | Объём четырёх изображений |
|---|---:|---:|
| Исходный RGB → PNG | 0,354 с | 1 860 140 байт |
| Абляция gray → PNG | 0,230 с | 1 058 220 байт |
| Новый gray → PGM | 0,136 с | 8 704 868 байт |

[Полные значения семи замеров и параметры среды](benchmarks/transport-linux-2026-10-14.json). Тайминги в общей виртуальной среде колеблются; это микроэксперимент, не SLA.

В этом эксперименте подготовка ускорилась примерно **в 2,6 раза (−62%)**. Это не скорость сканирования: здесь **не измерялись** передача stdin в реальный Tesseract, декодирование Leptonica, распознавание, запуск spawn, поиск и экспорт. PGM увеличил объём передачи относительно RGB PNG примерно в 4,7 раза. Он экономит сжатие, но сквозной выигрыш и память всей группы процессов требуют замера. На цветных документах преобразование в серый также нужно проверить по полноте распознавания.

Формула ожиданий: если подготовка занимала долю `f` общего времени, ускорение только этого участка в 2,6 раза даёт общий коэффициент `1 / ((1-f) + f/2.6)`, а не 2,6 автоматически.

## 4. Оставшиеся риски и лучшие следующие решения

### P1 — наблюдаемость и корректность результатов

1. **60 секунд — на весь PDF, не на страницу** (`scanner._run_isolated`, `AppSettings.per_file_timeout`). При нескольких десятках страниц процесс может быть убит, а готовые страницы не возвращаются: сейчас единственный результат отправляется после окончания файла. Решение: протокол page-result/heartbeat, отдельный page timeout, общий ограниченный бюджет документа, явный статус «частично прочитан». Не отменять watchdog и не повышать таймаут бесконечно. Для диагностики существующая настройка `--timeout 300` позволяет отличить медленный документ от сбоя, но это не оптимизация.

2. **Неполный текстовый слой может отключить OCR там, где он нужен** (`PdfReader.extract_text`). Например, номер страницы/штамп распознаётся как нормальный текст, а основное содержимое — изображение. `_looks_garbled` и порог 30 символов не являются измерением качества. Решение: корпус смешанных PDF; оценка покрытия текстовых блоков и изображений, confidence/TSV, проверка полноты контрольных терминов. Не делать OCR всех страниц безусловно.

3. **Диагностика из spawn не поступает автоматически в родительский GUI/CLI.** Добавленная сводка `tier/models/lang/workers/pages/retries/attempts/failures/render/ocr_success_sum/wall` доступна в прямом benchmark при настроенном logger. В обычном сканировании дочерний процесс не наследует его handlers. Решение: ограниченные структурированные события через IPC, агрегация в родителе. `ocr_success_sum` — сумма wall-time успешных OCR-вызовов, не CPU-time и не полное wall-time файла. Не пересылать текст документов в диагностические события.

4. **Полнота DOC/DOCX**: DOC-эвристика считается успешной уже при коротком извлечённом тексте; fallback XML DOCX может пропустить повреждённую часть и вернуть успех. Решение: отдельные признаки качества/partial, набор эталонных сложных таблиц, altChunk, колонтитулов, legacy OLE. Повтор внешними программами не должен включаться только по отсутствию вообще любого текста.

### P1/P2 — архитектура производительности

5. **Главный кандидат на крупное ускорение — повторная загрузка OCR-моделей.** Сейчас каждая страница = новый процесс Tesseract. Эксперимент: persistent `TessBaseAPI` внутри изолированного worker (например, через опциональный tesserocr) против CLI. Альтернатива — небольшой batch страниц одному CLI-процессу. Для API нужны упаковка под Windows, корректное владение движком, перезапуск после N страниц/RSS, жёсткая отмена. Для batch — приватные временные файлы, корректное разделение страниц и восстановление после сбоя. Не внедрено без измерений и проверки поставки.

6. **Фиксированное распределение CPU не адаптируется к нагрузке.** `_RISKY_PROCESS_LIMIT` ограничен четырьмя процессами; `_OCR_LIMIT_PER_PROCESS` делит CPU на это число независимо от реального количества PDF, а внутри reader максимум четыре страницы. Один длинный PDF может недоиспользовать CPU, а смешанная очередь DOC/PDF блокировать слоты. Рекомендуемая схема: единый бюджет активных OCR-процессов и raster bytes на всё сканирование + отдельные очереди лёгких ридеров/тяжёлых файлов; свободные слоты доступны одному длинному документу. Проверять 1/2/4 workers и CPU affinity/container limits, не просто повышать `--workers` до 128.

7. **Spawn на каждый PDF/DOC и компиляция поисковых структур в каждом новом процессе.** Для большого количества маленьких файлов запуск может стоить дороже чтения. Решение: измерить startup/import отдельно; затем supervised persistent workers с recycle, сохраняя возможность убить конкретный зависший процесс. Обычный вечный `ProcessPoolExecutor` без watchdog не равноценен текущей изоляции.

8. **Нет постоянного кэша извлечения текста**, несмотря на поля `cache_hits/cache_misses` в `ScanStats`. Повторный поиск по тем же сканам снова делает OCR. Кандидат: opt-in локальный SQLite-кэш текста/страниц, отдельно от поисковых результатов. Ключ: идентичность/хеш файла + версия extractor/Tesseract + хеши моделей + язык/DPI/лимит страниц. Один writer, атомарные записи, квота, TTL, очистка. Для служебных документов обязательно учитывать ACL, шифрование и политику хранения; ошибки и partial не кэшировать как полный успех. Не включать скрытый дисковый кэш по умолчанию.

9. **Двойной обход сетевого дерева** (`precount_files=True`). Для SMB стоимость уже не «почти бесплатна». Использовать существующий `--no-precount` для быстрого старта либо один discovery-проход с неопределённым прогрессом; фиксировать discovery_seconds. Оптимизировать отдельно от OCR.

### P2 — безопасность, память и поддерживаемость

10. **Разрушительные операции не транзакционны.** Исправлен конкретный cleanup-дефект; остаются окна TOCTOU между проверкой идентичности, переименованием и unlink в изменяемом другим процессом каталоге. Нужны проверки конкурентной подмены, платформенные handle-based операции, отказ при смене идентичности. Перезапись/переименование не гарантируют физического удаления на SSD/CoW/снимках — имеющиеся предупреждения GUI сохранить. Для высокой гарантии нужны шифрование и уничтожение ключа/администрирование носителя.

11. **SMTP:** opt-in `save_password` сохраняет пароль в переносимом JSON; `security='none'` допускает незашифрованный транспорт. Предпочтительны OS credential store/секрет окружения, предупреждение или запрет auth без TLS, лимиты размера вложений. Существующая проверка TLS-сертификатов — плюс. Не копировать конфиги с секретами в логи/отчёты.

12. **Память результатов и UI:** все совпадения с несколькими контекстами хранятся в `ScanReport`, экспорт/GUI могут усиливать расход. При 1000 терминах × 50 результатов на файл это существенно. Нужны streaming export, глобальная квота/пагинация и контекст по запросу. Измерять задержки UI p95, объём очереди и суммарный RSS, не только время OCR.

13. **Поисковая семантика:** устранено различие перекрытий; остаётся необходимость дифференциальных/property-based тестов regex/Aho на Unicode и разных порогах. `casefold` и `re.IGNORECASE` не полностью эквивалентны (например, dotless i). Порог 32 следует выбирать по измерениям, а не считать Python Aho всегда быстрее regex на C.

14. **Зависимости/структура:** в основном нижние границы версий, нет воспроизводимого lock/constraints релизной сборки. В текущей среде PyMuPDF 1.28.2 уже предупреждает о deprecated `fitz`. PDF-reader и benchmark уже предпочитают `pymupdf` с fallback на старый импорт. Зафиксировать проверенную матрицу зависимостей, обновлять контролируемо и проверить нижнюю поддерживаемую версию. Разделять `main_window.py` (~3000 строк), `results_model.py` (~1000), `scanner.py` (~800) по обязанностям после добавления контрактных тестов, не устраивать косметический массовый рефакторинг одновременно с OCR.

## 5. План экспериментов и критерии приёмки

### Шаг A: небольшой эталонный корпус

Не загружать служебные документы в Git. Локально подготовить 50–100 страниц: хороший русский скан, мелкий шрифт, перекос/шум, смешанные языки, таблицы, печати, пустые страницы, PDF с частичным текстовым слоем; отдельно 1 длинный PDF и много одностраничных. Для каждой группы вручную отметить контрольные термины и ожидаемые страницы, для части — полный текст.

Зафиксировать OS/CPU/RAM, Tesseract version, источник и SHA-256 traineddata, все параметры. Измерять cold/warm раздельно, минимум 5 повторов, не смешивать разные модели в сравнении baseline/candidate.

### Шаг B: измерить сквозной эффект уже внесённых правок

```bash
# Только подготовка, без OCR
python tools/benchmark_ocr.py --pdf scan.pdf --pages 10 --repeats 5

# Реальный PdfReader/OCR, без обхода каталогов и spawn оркестратора
python tools/benchmark_ocr.py --ocr --pdf scan.pdf --pages 10 --repeats 5 \
  --tesseract /path/to/tesseract --tier fast --workers 2 --russian-only

# Интеграционная проверка протокола stdin; требуется eng.traineddata
DSP_TEST_TESSERACT=/path/to/tesseract python -m pytest tests/test_pdf_reader.py -k real_tesseract

# Полный путь сканера (таймаут 300 здесь только диагностический)
python main.py --cli --no-config --path /path/to/corpus --types pdf \
  --content-terms 'договор' --ocr-model-tier fast --russian-only \
  --workers 2 --timeout 300 --no-precount --format csv --output report.csv
```

На Windows переменную smoke-теста установить через PowerShell `$env:DSP_TEST_TESSERACT = 'C:\...\tesseract.exe'`. Команды запускать на baseline и candidate с одинаковым корпусом/моделями; benchmark нового конвейера можно использовать отдельно от полного scanner.

Метрики: end-to-end wall, pages/sec, file/page p50/p95, суммарный пиковый RSS дерева процессов, число запусков/повторов, таймауты, term recall, ложные совпадения; при эталонном тексте CER/WER. Поля `characters`, `term_occurrences`, `text_sha256` из benchmark — диагностические признаки, **не** полноценные метрики качества.

Критерий: сохранение всех контрольных находок, отсутствие новых тихих пропусков/зависаний, ограниченная память, подтверждённый выигрыш на целевой машине. Если PGM не ускоряет полный путь, оставить безопасный планировщик, сравнить gray PNG и откатить только транспорт.

### Шаг C: крупные изменения — по одному

1. Передача метрик/частичных статусов из child → parent и раздельные таймауты.
2. Общий бюджет OCR/памяти.
3. Сравнение persistent API / batch CLI / текущего CLI.
4. Opt-in кэш для повторных проходов с политикой безопасности.
5. Только затем tuning DPI/PSM/предобработки по группам документов.

**Не делать вслепую:** PSM 6 для всех документов, уменьшение DPI, отключение retry/инверсии, прекращение чтения после первого найденного слова, повышение числа потоков. Такие изменения могут «ускорить» поиск ценой незаметной потери нужных результатов.
