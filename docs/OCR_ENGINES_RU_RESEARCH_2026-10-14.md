# OCR для русского текста: альтернативы Tesseract для DSP Scanner

**Дата проверки: 14 октября 2026 года.**

> **Дополнение после исследования:** проведены локальные замеры девяти конфигураций. На синтетическом корпусе Tesseract Fast оказался быстрее RapidOCR, а постоянный Tesseract API сократил время `rus+eng` на 11,2%. См. [отчёт с методикой и ограничениями](OCR_ENGINE_BENCHMARK_2026-10-14.md). Ниже сохранены исходные исследовательские рекомендации, сформулированные до замеров.

## Решение в одном абзаце

**Первый кандидат для локального A/B-теста — RapidOCR + ONNX Runtime с явно выбранным кириллическим распознавателем PP-OCRv5 mobile (`cyrillic` и отдельно `eslav`).** Это рекомендация для эксперимента, не доказанный победитель по скорости. Параллельно стоит измерить Tesseract Fast через переиспользуемый `TessBaseAPI`: в текущем проекте новый процесс Tesseract запускается на каждую страницу. Яндекс действительно предлагает **Vision OCR**, но публичные GitHub-репозитории, которые удалось проверить, предоставляют API-клиенты, примеры и датасет, а не открытый локальный движок. Облачную обработку нельзя автоматически включать для потенциально служебных документов. Подробности и источники ниже.

## Границы исследования

Проверены официальные документы, исходники/конфигурации и releases GitHub, GitHub Issues/Discussions RapidOCR и Docling, документация PaddleOCR и Tesserocr, публикация MWS AI на Хабре и её комментарии, материалы Microsoft и коммерческих поставщиков. Старые форумные сравнения и SEO-таблицы без воспроизводимой методики не использованы как доказательство производительности.

**Прочитать «все профессиональные форумы» невозможно**: это целевая выборка, а не исчерпывающий обзор всего интернета. Отдельно проверены первоисточники для наиболее важных выводов. В этой итерации новые OCR-движки не устанавливались и не запускались; пользовательские документы не передавались внешним API. Код приложения и зависимости не менялись — подготовлен исследовательский отчёт.

Достоверность сведений разделена на:

## 1. Что именно есть у Яндекса

### Vision OCR

В актуальной официальной документации перечислены `page`, `page-column-sort`, `handwritten`, `table`, `markdown`, `math-markdown`. Поддержка рукописного текста на русском и английском прямо указана, в том числе для `page`. API — REST/gRPC; это сервис распознавания, а не ЯндексGPT, которому нужно просить «перепечатать документ». Страница моделей была прочитана непосредственно, поскольку старые поисковые сниппеты уже расходятся с ней: [актуальные модели](https://aistudio.yandex.ru/ru/docs/vision/concepts/ocr/models), [описание API](https://aistudio.yandex.ru/ru/docs/vision/concepts/ocr/).

Официальный `yandex-cloud-examples/yc-vision-ocr-recognizer` получает документы из Object Storage и отправляет их в Vision. Возможность «запустить скрипт локально» означает локальный **клиент**, а не локальное выполнение OCR. [1](https://github.com/yandex-cloud-examples/yc-vision-ocr-recognizer)

В `yandex-cloud/ocr` лежат сравнение облачных сервисов, метрики и датасет русского текста «в естественной среде»: вывески, объявления, обложки и т. п. README описывает использование ключей облачных API. Это не архив открытых весов и не эталон скорости обработки офисного A4. Проверено через GitHub API: [репозиторий](https://github.com/yandex-cloud/ocr), [README сравнения](https://github.com/yandex-cloud/ocr/blob/master/ocr_comparison/README.md).

**Я не нашёл в проверенных официальных репозиториях публично скачиваемый автономный движок Vision OCR с весами.** При этом у Yandex AI Studio есть коммерческое on-premises предложение. Прочитанная страница описывает составные модули/лицензии и инфраструктуру, но явно не подтверждает поставку именно Vision OCR в нужной нам конфигурации. Поэтому утверждение «у Яндекса вообще нет on-prem» было бы слишком сильным: конкретную поставку OCR нужно уточнять у вендора. [On-premises](https://aistudio.yandex.ru/en/on-premises)

### Может ли Яндекс быть быстрее?

Для этого проекта **пока неизвестно**. Нужен end-to-end замер с загрузкой изображения, сетью, очередью, распознаванием и получением результата. Освобождение CPU клиента не означает меньшую задержку. В просмотренных источниках не найдено воспроизводимого сравнения текущего Vision OCR и нашего Tesseract Fast на одном русском PDF-корпусе.

Сервис тарифицирует успешное распознавание постранично; повторное распознавание того же изображения — отдельная единица. Тариф зависит от модели и договора, поэтому старые форумные «копейки за страницу» не являются актуальным расчётом бюджета. [1](https://aistudio.yandex.ru/docs/en/vision/pricing.html)

Для DSP Scanner это **опциональный облачный backend только после явного разрешения**. Даже отключение серверного логирования не устраняет передачу документа поставщику. Нужны согласование состава данных, условий хранения и договора. Автоматического облачного fallback быть не должно.

## 2. Приоритетный локальный кандидат: RapidOCR

RapidOCR предоставляет несколько вариантов исполнения OCR-моделей, включая ONNX Runtime и OpenVINO. В таблице поддерживаемых моделей есть PP-OCRv5 `cyrillic` mobile и `eslav`; поддержка кириллицы зависит от конкретного распознавателя, не от слова «multilingual» в описании библиотеки. [5](https://github.com/RapidAI/RapidOCRDocs/blob/main/docs/model_list.md)

На момент проверки GitHub API показывал release **v3.10.0 от 2026-10-08**. В проверенной конфигурации этого релиза:

- доступны `cyrillic_PP-OCRv5_rec_mobile` и `eslav_PP-OCRv5_rec_mobile`;
- ONNX Runtime имеет отдельные `intra_op_num_threads` / `inter_op_num_threads`;
- присутствует выбор execution provider;
- веса загружаются отдельно, в `default_models.yaml` есть URL и SHA-256.

Первоисточники: [релиз](https://github.com/RapidAI/RapidOCR/releases/tag/v3.10.0), [конфигурация v3.10.0](https://github.com/RapidAI/RapidOCR/blob/v3.10.0/python/rapidocr/config.yaml), [маршрутизация моделей v3.10.0](https://github.com/RapidAI/RapidOCR/blob/v3.10.0/python/rapidocr/default_models.yaml).

### Почему я предлагаю проверить его первым

Это инженерный выбор по соответствию проекту:

1. Возможна локальная обработка без отправки документов третьим лицам.
2. Для ONNX-варианта не требуется включать PaddlePaddle как основной inference runtime.
3. Можно держать сессии детекции/распознавания загруженными, а не инициализировать их для каждой страницы.
4. Есть отдельные русско-кириллические mobile-модели.
5. Можно сравнить ONNX Runtime и OpenVINO на целевом CPU, сохраняя один набор весов.

Код RapidOCR имеет Apache-2.0; лицензии конкретных моделей/зависимостей всё равно следует фиксировать отдельно. Размер файла recognizer — **не** размер всего приложения: ещё нужны detector, runtime и зависимости. [Лицензия RapidOCR](https://github.com/RapidAI/RapidOCR/blob/v3.10.0/LICENSE)

### Почему нельзя обещать, что он быстрее

В обсуждении RapidOCR #213 maintainer связывает время с количеством текста на изображении: пользователь сообщал о долгой работе на одном ядре. [1](https://github.com/RapidAI/RapidOCR/discussions/213)

В issue #514 пользователь на Windows 11, RapidOCR 3.2.0 и ORT 1.21 сравнил одинаковые PP-OCRv4 server-модели: detector RapidOCR оказался медленнее варианта PaddleOCR; приведены измерения отдельных стадий. Это историческое частное сравнение, не приговор нынешнему релизу, но опровержение правила «ONNX автоматически быстрее». [5](https://github.com/RapidAI/RapidOCR/issues/514)

В Docling #4167 обсуждается стоимость поиска алгоритмов свёртки на GPU при меняющихся размерах входа. Наличие GPU само по себе ничего не гарантирует. [7](https://github.com/docling-project/docling/issues/4167)

**Вывод:** сравнивать нужно связку «модель + её preprocessing + runtime + provider + потоки + жизненный цикл», а не названия Python-пакетов.

## 3. PaddleOCR и важная ловушка PP-OCRv6

### PP-OCRv5

Русские модели есть, но стандартный `PP-OCRv5_mobile_rec` не следует путать с `cyrillic_PP-OCRv5_mobile_rec`. Для русского нужно явно выбрать соответствующий языковой checkpoint и словарь. [Конфигурация моделей](https://github.com/RapidAI/RapidOCR/blob/v3.10.0/python/rapidocr/default_models.yaml)

Официальный benchmark PP-OCRv5 показывает существенную разницу mobile/server и стоимости дополнительных стадий. Например, в его CPU-эксперименте mobile — 1,75 с/изображение, server — 4,34 с. Это данные другого железа/набора изображений, **их нельзя непосредственно сравнивать с нашими 0,661 с за две страницы**. [3](https://paddlepaddle.github.io/PaddleOCR/main/en/version3.x/algorithm/PP-OCRv5/PP-OCRv5.html)

Для нашего поиска не нужны Markdown, распознавание диаграмм и полный PP-Structure pipeline на каждой странице. Моя рекомендация — сначала минимальные text detection + recognition; orientation/unwarping включать по измеримой необходимости.

### PP-OCRv6: быстрый, но какой язык?

Актуальная документация PP-OCRv6 обещает существенно более быстрые варианты tiny/small/medium. Однако её описание общего recognition-моделя говорит о китайском, английском, японском и латинских языках. В проверенных language routes RapidOCR **v3.10.0** в наборах стандартного v6 нет `ru`, `cyrillic` или `eslav`. Поэтому результат «v6 tiny 0,22 с на ONNX CPU» нельзя использовать как доказательство скорости русского OCR. Это видно прямо в [исходной конфигурации релиза](https://github.com/RapidAI/RapidOCR/blob/v3.10.0/python/rapidocr/default_models.yaml) и [документации PP-OCRv6](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv6/PP-OCRv6.en.md).

Это ограничение относится к **стандартному распознавателю**, а не к невозможности строить какие-либо русские OCR-конвейеры с компонентами v6.

Обнаружено community-дообучение **PP-OCRv6 Tiny RU ONNX** от `vladlinv`. В model card описаны русский текст, рукопись, собственный benchmark и настройка padding через изменение `resize_norm_img`. Это перспективный **экспериментальный** кандидат, но не стандартная модель Baidu и не drop-in обновление нашего OCR. До включения нужно проверить лицензию именно checkpoint, версию runtime, точность на независимом корпусе и стабильность preprocessing. Приведённые автором CER/WER — не наши измерения. [8](https://huggingface.co/vladlinv/PP-OCRv6_tiny_rec_ru_onnx)

Второй возможный эксперимент — быстрый v6 detector + v5 Cyrillic recognizer, но качество детекции русского и совместимость такой конфигурации тоже должны быть проверены, а не предполагаться.

## 4. Не обязательно менять движок: Tesseract через API

В `app/readers/pdf_reader.py` текущая реализация по-прежнему выполняет `_run_tesseract()` на каждую страницу. Предыдущие изменения сократили подготовку изображения и устранили простои, но не убрали запуск процесса и повторную загрузку моделей.

`tesserocr` — обёртка над C++ API Tesseract, а не новый распознаватель. README показывает использование `PyTessBaseAPI` для серии изображений; Cython-обёртка освобождает GIL во время обработки. [1](https://github.com/sirfz/tesserocr)

**Моя рекомендация:** отдельная экспериментальная ветка конфигурации `Tesseract Fast / persistent API`, с одним API-объектом на worker, а не одним общим объектом на произвольные потоки. Сохраняются родительский watchdog, изоляция нативного кода и ограниченный срок жизни worker. Обязательно проверить перенос состояния между страницами и порядок обработки: повторное использование API требует собственных регрессионных тестов.

Возможный выигрыш особенно интересен для множества небольших страниц. Для плотного листа, где доминирует собственно распознавание, он может быть скромным. **Локального замера API в этом исследовании нет.**

## 6. Что показали профессиональные обсуждения

### Хабр: полезная работа, но не готовый ответ для нашего архива

В статье MWS AI приведены 193,1 стр/мин для Tesseract и 143,5 для RapidOCR. Однако использованы **15 примеров рукописного русского**, а CER/WER не считались. Это не доказательство качества на печатных документах и не доказательство, что RapidOCR быстрее нашего Fast. [1](https://habr.com/ru/companies/mts_ai/articles/1065182/)

В комментариях автор подтвердил: стр/мин пересчитаны из маленькой выборки; прогрев затронул только часть типов документов; отдельного cold-start замера не было; перенос выводов с рукописи на печатные документы сформулирован слишком сильно. Это особенно важные оговорки. [Комментарии к исследованию](https://habr.com/ru/companies/mts_ai/articles/1065182/comments/)

### GitHub: повторяющиеся практические проблемы

- Выбран неправильный языковой checkpoint: приложение «поддерживает русский», а загружает китайский/латинский recognizer. Это отдельно поднималось в Docling. [4](https://github.com/docling-project/docling/issues/3433)
- Новые размеры текстовых строк вызывают дорогой подбор GPU-алгоритмов. [7](https://github.com/docling-project/docling/issues/4167)
- Детектор, а не recognizer, становится главным узким местом. [5](https://github.com/RapidAI/RapidOCR/issues/514)
- Много внешних workers конфликтуют с внутренним параллелизмом. В обсуждении OpenVINO maintainer предложил уменьшить число workers. [4](https://github.com/RapidAI/RapidOCR/discussions/386)
- Разница архитектуры контейнера/хоста может определять минуты вместо секунд, а не выбор OCR-модели. [6](https://github.com/RapidAI/RapidOCR/discussions/156)

Эти issues — сообщения о конкретных конфигурациях, иногда старых и уже изменённых. Они используются как **список рисков для проверки**, не как утверждение, что текущие релизы обязательно неисправны.

## 7. Как принимать решение для DSP Scanner

### Этап 1: три обязательных участника

1. **A — текущий Tesseract Fast CLI**, `rus` и `rus+eng`, уже измеренный и покрытый тестами.
2. **B — Tesseract Fast persistent API**, те же веса и ограничения CPU.
3. **C — RapidOCR 3.10.0 + PP-OCRv5 mobile**, отдельно `cyrillic` и `eslav`, ONNX Runtime CPU.

Следом: OpenVINO на целевой Intel-машине, experimental Tiny RU, платный SDK при наличии бюджета. Облачный Яндекс — только отдельный разрешённый сценарий, не участник скрытого fallback.

### Этап 2: одинаковые данные и ресурсы

Нужны 100–300 репрезентативных обезличенных страниц пользователя: чистый печатный русский, мелкий шрифт, таблицы, двухколоночная вёрстка, печати, низкий контраст, перекосы, смешанные RU/EN; рукопись — отдельная группа, если нужна. Синтетический корпус из предыдущего этапа оставить smoke-тестом, не единственным доказательством.

- одинаковый лимит CPU/RAM и исходные страницы;
- корректный собственный preprocessing каждого recognizer, но без скрытого уменьшения изображения до потери мелкого текста;
- cold-start отдельно от warm throughput;
- одинаковый бюджет внешнего и внутреннего параллелизма;
- инициализацию модели показывать отдельно, не вычитать только у одного конкурента;
- реальные повторы, p50/p95, pages/sec, суммарный RSS дерева процессов;
- измерять render → detection → recognition → postprocess → search, а также полный scanner wall-time;
- сохранять имя/hash модели, runtime/provider, число потоков и число пропущенных страниц.

Главная метрика для проекта — **полнота нахождения контрольных терминов**, затем ложные находки и CER/WER. Быстрый движок, пропускающий слово «договор» или номер документа, неприемлем даже при красивом pages/sec. Число возвращённых символов и confidence сами по себе не измеряют точность; confidence разных движков нельзя сравнивать напрямую.

Предлагаемый практический порог внедрения: отсутствие потерянных контрольных находок и повторяемое снижение медианного времени хотя бы на 20% на целевой нагрузке, без неприемлемого роста p95/RSS. Это **критерий приёмки**, не прогноз выигрыша RapidOCR.

### Этап 3: подключение без ломки приложения

Рекомендую разделить два понятия:

```text
backend: tesseract_cli | tesseract_api | rapidocr | optional_cloud
profile: конкретный набор моделей и параметров этого backend
```

`fast` Tesseract не должен означать тот же файл/режим, что `mobile` Paddle. Нужен общий результат страницы: `text`, `page_index`, `boxes`, `confidence` (с указанием источника), `timings`, `model_id`, `warnings`, `partial`.

Рендер PDF остаётся в потоке-владельце PyMuPDF. Модели живут в ограниченном числе изолированных workers, а не создаются для каждой страницы. Watchdog, отмена и восстановление после сбоя обязательны. Кэш, если появится, привязывается к файлу и версии/хешу **конкретной модели**.

Не включать автоматическое повторное распознавание каждой страницы без найденного ключевого слова: большинство документов могут действительно не содержать термин, и такой fallback удвоит работу. Решение о повторе должно опираться на проверенные признаки плохого OCR/покрытия текста или явный режим пользователя. Никаких незаметных отправок в облако.

## Итог

- **Есть смысл искать быстрее — да.**
- **Доказано, что найденный движок быстрее нашего Tesseract Fast на пользовательских PDF — нет.**
- **Наиболее рациональный следующий эксперимент:** RapidOCR PP-OCRv5 Cyrillic/Eslav против текущего Tesseract и его persistent API.
- **Если важен именно Яндекс:** Vision OCR существует и ориентирован в том числе на русский текст, но публичная GitHub-интеграция не равна локальному open-source движку; скорость/стоимость/конфиденциальность проверять отдельно.

Предыдущие локальные результаты Tesseract и методика находятся в [OCR_SETUP.md](OCR_SETUP.md). В этом отчёте чужие числа не выдаются за наши новые замеры.
